    turn_pipeline.md — 33 个 turn_*.py 分阶段走读¶

    文件概览¶

    conversation_loop.py 只负责"把阶段串起来"，每个阶段的真正逻辑都住在 agent/turn_*.py 的独立文件里（agent/AGENTS.md：Each phase of an iteration is its own sibling——改一处 溢出处理只动一个 ~600 行的文件）。agent/ 下共有 33 个 turn_*.py，本文按 turn 生命周期分五幕走读：

    ① 上下文构建（一次/turn）      turn_context / turn_context_compaction / turn_preflight / turn_preflight_gate / turn_scripted_prelude
② 迭代准备与请求组装（一次/迭代） turn_iteration_prep / turn_request_assembly / turn_api_request
③ API 调用与错误（一次/尝试）    turn_api_call / turn_api_error / turn_response_check / turn_response_intake / turn_retry_state
④ 恢复分支（出错时）            turn_recovery / turn_overflow / turn_truncation / turn_empty_response / turn_recovery_autorecover / turn_recovery_codex
⑤ 工具轮与收尾（回答成型时）     turn_tool_round / turn_tool_validation / turn_final_response / turn_stop_gates / turn_finalizer / turn_usage / turn_summary / turn_liveness / turn_loop_errors / turn_explainers / turn_failure_copy / turn_author
（准入门面，另有专文）           turn_facade / turn_facade_lease → 见 turn_facade.md

    所有阶段函数遵循同一协议：接收 _LoopState 的同名字段、返回带 action 的 verdict （fallthrough / return / break / continue），由 _run_phase 按名传参回拷。

    关键代码走读¶

    第一幕：turn 上下文构建（每 turn 一次）¶

    build_turn_context —— 一次性的赛前准备（turn_context.py:1189）

    # agent/turn_context.py:1189-1206（节选）
def build_turn_context(agent, user_message, system_message, conversation_history,
                       task_id, stream_callback, persist_user_message, ...) -> TurnContext:
    """Run the once-per-turn setup and return the loop's input context.

    Helpers are passed in to avoid an import cycle with ``agent.conversation_loop``.
    Order matters: the DB session row is created only AFTER the system prompt is built
    (else it persists system_prompt=NULL and costs a cache miss) and BEFORE preflight
    compression."""

    docstring 末尾的 "Order matters" 是这一幕的灵魂：会话行必须在系统提示词之后、preflight 压缩之前创建——先建行会落一条 system_prompt=NULL 的记录，下次恢复触发警告外加一次 前缀缓存 miss（#45499）。内部按序做：安全 stdio → turn_author 解析 → 旋转会话恢复 → 绑定 task/turn id → 复制历史 → 追加用户消息并记 current_turn_user_idx → 恢复/构建系统 提示词 → 建会话行 → run_turn_start_compaction → 插件 pre_llm_call → 内存预取 → 盖 api_content sidecar 章 → _persist_turn_start（第一次 LLM 调用前就持久化用户消息）。 成品 TurnContext（:546-561）的字段即循环要读的输入：messages、active_system_prompt、 current_turn_user_idx、plugin_block_message（否决：turn 以此结束、不做推理）等。

    三遍 turn 起始压缩（turn_context_compaction.py:129）：run_turn_start_compaction （docstring："Idle compaction, then preflight compression (or the uncompressed guard)"）先跑 _idle_compaction 再跑 _preflight_compression，产出 CompactionOutcome（重建后的 messages/系统提示词/历史/user 下标 + compressed/blocked 旗标）。第一遍 idle（:144）： opt-in——距上次活动超过 idle_compact_after_seconds 才估算 token，够闲且超 floor 才压。 第二遍 preflight（:230）：超阈值时最多跑 max_compression_attempts（默认 3）个 pass （_run_preflight_passes，:352），"行数和 token 都没动"或"进度不足"就 blocked=True 收手 防抖动；引擎接管时只跑一次维护 pass（:436）。第三遍：压缩被禁用时 _rearm_uncompressed_overflow_warn（:479）重新武装溢出告警。细节（#98722）：压缩耗尽 主机感知的进度超时——这个 preflight 迭代根本没碰 provider，要退还 api_call_count 和预算（_refund_api_call，:103）并终止 turn。

    run_preflight_gate —— 发请求前的压力门（turn_preflight_gate.py:20）：它比较完全组装 后的请求（含 api_content/插件注入/prefill/MoA 上下文），不是裸 messages（:72-79 注释）； "上次压缩没取得足够进度"就置 _preflight_compression_blocked=True 封锁本轮主动压缩 （provider 报错后的被动通道保留）。同时处理 Ollama 运行时窗口过小的终局（:46-58，退还计数 并 break）。turn_preflight.py 提供两个压缩时机：run_preflight_compression（:57，上面 那道门的实现体）与 compress_after_tool_results（:245，工具结果回填后的第二次时机）。

    turn_scripted_prelude.py —— 剧本式工具前奏（play_prelude:57）：桌面向导要在第一次模型 调用之前自己演几个工具步骤？Prelude 是调用方持有的生成器，每步 yield (assistant 文本, 工具名, 参数)，走完全一样的 run_tool_round（先持久化再执行、照发事件）， 工具结果 send 回生成器供后续步骤使用；play_prelude 返回 ("return", result) / ("break", None) / ("run", None) 三种裁决。角色序列保持 user → assistant(tool_calls) → tool → ... → assistant(模型)，不计 API 调用、不发 pre/post_api_request 钩子——缓存不变量完好。

    第二幕：迭代准备与请求组装（每迭代一次）¶

    begin_iteration —— 迭代入口（turn_iteration_prep.py:352）：docstring 概括顺序—— "apply a pending redirect, reset the checkpoint dedup, then the interrupt / review-budget / iteration-budget exits；api_call_count 在这里自增（宽限调用消费 flag 而非预算）"。 prepare_iteration（:144）做提示词刷新 epoch 检查；announce_api_call（:307）负责转圈 动画与请求日志。宽限调用（_budget_grace_call，:408-416）：预算耗尽后允许模型多调一次 产出体面总结，flag 用完即清。

    assemble_api_request —— 装饰副本 + cache plan 最后构建（turn_request_assembly.py:106）

    # agent/turn_request_assembly.py:106-113 + 189-231（节选）
def assemble_api_request(agent, *, messages, current_turn_user_idx, _ext_prefetch_cache, ...) -> AssembledRequest:
    """Assemble the request in the original order. ORDER IS LOAD-BEARING: cache breakpoints
    are injected only after whitespace normalization, the orphan sweep, thinking-only drop /
    user merge and surrogate stripping, so the same row's bytes never vary across turns."""
    ...
    api_messages, effective_system = build_api_messages(          # turn_context.py:1418
        agent, messages, current_turn_user_idx=current_turn_user_idx, ...)
    ...
    # Normalize whitespace and tool-call JSON for bit-perfect prefixes across turns
    # (KV-cache reuse on local servers, better cloud cache hits); API copy only.
    for am in api_messages:
        if isinstance(am.get("content"), str):
            am["content"] = am["content"].strip()
    _canonicalize_api_tool_calls(api_messages)
    ...
    # Build the request-local cache sections LAST, after every transcript mutation.
    if agent._use_prompt_caching and agent.provider != "moa":
        _initial_cache_plan = build_prompt_cache_plan(...)
        api_messages = _initial_cache_plan.messages
        tools_for_api = _initial_cache_plan.tools

    三个核心概念：

    1. 装饰副本：build_api_messages（turn_context.py:1418-1531）对 messages 逐条结构化 克隆（嵌套容器绝不共享）；历史行重放"当初发送的精确字节"（api_content sidecar）。 messages 本体除了 sidecar 章绝不被触碰。
    2. bit-perfect 缓存前缀：空白归一化、孤儿工具结果清扫、thinking-only 丢弃、相邻 user 合并、代理剥离——全在打缓存断点之前。顺序错了，同一行的字节在不同 turn 间漂移， 缓存永远 miss。
    3. cache plan 最后构建：build_prompt_cache_plan 在所有转录变异完成后才执行， 只装饰请求副本，canonical 工具注册表原样。

    AssembledRequest（:24-37）action 恒为 "fallthrough"，字段是迭代要用的 api_messages/tools_for_api/approx_tokens/request_pressure_tokens 等。压力估算三级： 锚定值（provider 真实 usage+delta）> 原生 Responses 剪枝估算 > 粗估 + 实际值托底 （_pressure_with_real_floor）。

    build_api_request —— 每次尝试的请求（turn_api_request.py:177）：docstring 点题—— "every mutation happens BEFORE middleware/hooks/debug dumps observe the payload"。与每迭代 一次的 assemble_api_request 不同，它在内层重试循环里每次尝试都跑：重新施加 reasoning echo pad、为当前 provider（fallback 后可能不同）重打缓存装饰、调 build_api_kwargs （chat_completion_helpers.py:1503）按 api_mode 分支构造 kwargs、代理/ASCII 检查点、 OpenRouter 缓存绕过、provider 请求头、中间件与 pre_api_request 钩子。

    第三幕：API 调用与错误（每尝试一次）¶

    perform_api_call —— 真正的模型调用（turn_api_call.py:72）

    # agent/turn_api_call.py:91-115（节选）
        if _use_streaming:
            return agent._interruptible_streaming_api_call(next_api_kwargs, on_first_delta=_stop_spinner)
        from agent import relay_llm

    两个落地实现在 agent/chat_completion_helpers.py（4,001 行）： interruptible_streaming_api_call（:3977，流式逐 delta 回调）和 interruptible_api_call （:1260，worker 线程上跑，让主循环随时检测中断；每个 worker 独立 per-request client， 中断只关那一条连接）。wire 适配在 agent/transports/：chat_completions.py（默认）、 anthropic.py、bedrock.py、codex.py（Responses）、codex_app_server.py（子进程运行时）。 调用被 run_llm_execution_middleware 包裹并在重定向锁保护的 _model_request_active 括号下 执行；响应返回后检查"重定向是否跨过了响应"（线程竞争 → 丢弃过时响应从纠正重建）。

    nous_rate_limit_guard（turn_api_call.py:232）：provider 是 nous 时先看剩余限额——另一 会话已撞限（含 SDK 重试，每次都计 RPH）就跳过本次调用；有 fallback 就武装重启（break）， 没有就把缓冲的限流文案作为失败结果返回。整个守卫包在 try/except 里——守卫自己永远不许 弄断 agent 循环。handle_api_error（turn_api_error.py:52）：内层 except Exception 的落点——解释器关闭检测（立即放弃）→ classify_api_error 分类（429/401/413/overflow/ content policy/billing…）→ 按类路由到恢复分支（第四幕）→ 不可重试的客户端错误终局 → 重试耗尽时 settle_unrecovered_error（:266）走"主传输恢复 → fallback 链 → 终局结果"。

    check_api_response —— 响应校验（turn_response_check.py:92）：顺序是——形状验证 （validate_response_shape，turn_recovery.py:1585；无效→重试/急切 fallback/终局）→ 推导 finish_reason → content_filter（HTTP-200 的内容政策拒绝是确定性的：试一次 fallback，否则 返回拒绝文案）→ length（进截断恢复）→ usage 折算（record_response_usage）。 normalize_model_response —— 响应整流（turn_response_intake.py:165）：把原始响应整流成 assistant_message（content 恒为 str）、拼接 agent-as-provider 投影、发 post_api_request 钩子、思考内容转发进度回调；两个续写守卫：未闭合的 <REASONING_SCRATCHPAD>（重试 2 次） 与 Codex incomplete（必要时激活 fallback 并同步系统提示词上的身份）。

    TurnRetryState —— 单次尝试的守卫账本（turn_retry_state.py:9-15）：dataclass docstring 点题——"One-shot recovery guards + restart signals for a single API-call attempt. A fresh instance is created per api_call_count iteration; each guard fires at most once, and restart_with_* signals tell the loop to rebuild and retry."。三十多个一次性布尔守卫 （OAuth 刷新 × 各 provider、thinking 签名、图片收缩、429、402 下调、auth failover……） 加四个重启信号（compressed / length_continuation / rebuilt / redirected）。每次迭代在主循环 新建一个（conversation_loop.py:1768）——每守卫最多触发一次，天然防死循环。

    第四幕：恢复分支（出错时才进）¶

    与其他模块的关系¶

    conversation_loop._run_phase 按名调用 33 个 turn_*.py；各阶段向外触达： prompt_caching.py（cache plan 缓存断点标记）→ chat_completion_helpers.py（真正的 HTTP 调用）→ agent/transports/（wire 适配）→ tool_executor + tool_dispatch_helpers（工具 执行，_MAX_TOOL_WORKERS=8）→ turn_finalizer（落到 session_persistence / context_compressor / background_review）。压缩算法层（context_compressor.py / conversation_compression.py）在 compression 专文详述，本目录只调门面（agent._compress_context、 should_compress、threshold_tokens）。结果 dict 契约（final_response/messages/ completed/failed/interrupted/failure_reason）被 gateway/CLI/TUI/Desktop/ACP 全部 消费；UI 错误卡依赖 turn_failure_copy + agent/error_surface.py。系统提示词在 build_turn_context 里恢复/构建，之后整个循环视其为只读（见 system_prompt.md）。

    总结¶

    • 33 个 turn_*.py 就是 turn 生命周期的分解：上下文构建（5）→ 迭代准备与请求组装（3） → API 调用与错误（5）→ 恢复分支（6）→ 工具轮与收尾（12）→ 准入门面（2）。
    • 顺序即正确性：提示词先建、会话行后建；先归一化再打缓存断点；cache plan 永远最后 构建——顺序错一个，前缀缓存就碎一个。
    • 三层请求概念：messages（canonical，绝不改）→ api_messages（结构化克隆的装饰副本） → api_kwargs（每次尝试重建，中间件后的最终 payload）。
    • 持久化不变量：用户消息在第一次 LLM 调用前落库；工具调用在第一个副作用前落库； canonical append 失败 = 终止 turn。
    • 恢复有界：每守卫一次（TurnRetryState）、每 turn 8 次外层异常、自动恢复 5 轮抖动 阶梯、重启退款由 restart_count 兜底——所有自动行为都有一条明示的天花板。
