    tool_execution.md — agent 侧工具执行：拦截表、段规划器、并发执行与护栏¶

    文件概览¶

    关键代码走读¶

    1. INLINE_TOOL_EXECUTORS：需要活 agent 状态的工具先行拦截¶

    一部分工具需要 AIAgent 的活状态（store、回调、session DB），不走 registry。两张历史上各自漂移的 if/elif 链（顺序路径与并发 invoke_tool）被收编成一张表：

    2. 段规划器：并行安全段 + 顺序屏障¶

    _plan_tool_batch_segments 把批次切成保序的段——后面的调用绝不越过前面的屏障， 结果顺序与副作用边界与全顺序执行完全一致：

    # agent/tool_dispatch_helpers.py:212-258（节选）
def _plan_tool_batch_segments(tool_calls, *, execution_cwd=None) -> list[tuple]:
    """Split a tool-call batch into ordered ("parallel"|"sequential", calls) segments.

    Call order is preserved exactly (a later call never crosses an earlier barrier) ...
    Path-scoped tools join a run only if they don't conflict with its reservations:
    reader↔reader overlap stays parallel; any overlap involving a writer closes the run ...
    Runs shorter than two calls demote to sequential ..."""
    segments: list[tuple] = []
    current: list = []
    reserved_paths: list[tuple[Path, bool]] = []   # (canonical_path, is_writer) 当前 run 的预约
    ...
    for tool_call in tool_calls:
        admission = _batch_admission(tool_call, execution_cwd)
        if admission is None:
            _close_parallel()
            _extend_sequential([tool_call])        # 屏障
            continue
        _name, scoped_paths, is_writer = admission
        if any((is_writer or existing_is_writer) and _paths_overlap(scoped_path, existing)
               for scoped_path in scoped_paths
               for existing, existing_is_writer in reserved_paths):
            _close_parallel()                      # 写冲突：关闭 run，重新开段
        reserved_paths.extend((p, is_writer) for p in scoped_paths)
        current.append(tool_call)
    _close_parallel()
    return segments

    准入分三类（_batch_admission，:182）：_NEVER_PARALLEL_TOOLS（clarify/manage_connections/ manage_catalog/setup_beat/set_theme——交互或用户可见）是屏障；_PATH_SCOPED_TOOLS （read_file/search_files 读，write_file/patch 写）按路径预约入场——读者可与读者共享 子树，写者与任何重叠者互斥；白名单 _PARALLEL_SAFE_TOOLS（web_search、skill_view 等无共享可变 状态）、无状态桥查（tool_search/tool_describe）与** opting-in 的 MCP 服务器工具**自由入场。 _peel_bridge_call（:137）先把 tool_call 桥拆到底层工具再判——否则 tool search 激活后所有 延迟工具都顶着同一个名字，悄悄丢失并发。段由门面侧消费：

    # run_agent.py:1308-1331（节选）
    def _execute_tool_calls(self, assistant_message, messages, effective_task_id, api_call_count=0):

        ...

    execute_tool_calls_segmented（tool_executor.py:1929）逐段派发：并行段给 execute_tool_calls_concurrent（ThreadPoolExecutor，_MAX_TOOL_WORKERS=8， _DEFAULT_CONCURRENT_TOOL_TIMEOUT_S=420s）、顺序段给 execute_tool_calls_sequential， 均以 finalize=False 跑；预算执行与 /steer 注入在全批结束只做一次 （_finalize_tool_batch）。

    3. 顺序路径：批准批次与"persist-before-execute"的执行侧¶

    顺序执行器外面还套一层终端批准批次——桌面场景要先把一批终端命令全部报批，再按原序放行执行：

    # agent/tool_executor.py:1859-1868
def execute_tool_calls_sequential(agent, assistant_message, messages, effective_task_id, api_call_count=0, *, finalize=True):
    from types import SimpleNamespace
    from agent.terminal_approval_batch import terminal_approval_batch, terminal_approval_runs
    for calls in terminal_approval_runs(agent, assistant_message.tool_calls):
        with terminal_approval_batch(agent, calls, messages, effective_task_id):
            _execute_tool_calls_sequential(agent, SimpleNamespace(tool_calls=calls), messages,
                                           effective_task_id, api_call_count, finalize=False)
        ...

    terminal_approval_batch.py 的模块注释点明分工："Workers keep execution middleware on its original stack. Only command approval runs ahead; the existing sequential executor releases each worker and persists its result before releasing the next. No terminal environment/cwd is acquired while preparing"——即批准可以预取，但每个结果先持久化再放行下一个（会话崩溃/中断时转录不缺行， 这就是 persist-before-execute 不变量在执行侧的形态），且准备阶段绝不预建终端环境。 顺序主体 _execute_tool_calls_sequential（:1871）在每个 call 前后检查 _interrupt_requested， 被打断时给未执行调用逐个补合成结果（_skip_remaining_sequential），保证 tool_call/tool_result 配对不破。

    4. 拦截表之外：registry 分发的三段守卫¶

    一次 registry 工具调用前后的护栏链是（_pre_tool_block → _dispatch_authorized_once → _run_agent_tool_execution_middleware）：ToolCallGuardrailController.before_call 先判——

    # agent/tool_guardrails.py:312-319（类定义节选）
class ToolCallGuardrailController:
    """Pure tool-call loop guardrail primitives.

    The controller is side-effect free: it tracks per-turn tool-call observations
    and returns decisions. Runtime code decides whether a decision becomes warning
    guidance, a synthetic tool result, or a controlled turn halt."""

    控制器是纯函数式的：连续相同 (tool, args, result) 第 3 次给 notice（STALL_GUARD_IDENTICAL_ CALL_THRESHOLD=3）、识别最长 4 期的 A,B,A,B 循环（每个整批算一"圈"）、no_progress 熔断； 幂等工具（读文件/搜索）不计数，terminal 等"失败即工作产出"的工具只对逐字重放熔断。 运行时决定一个 decision 落成警告、合成结果还是受控停转（toolguard_synthetic_result / append_toolguard_guidance）。结果侧由 tool_result_classification 供分类事实：has_failure_marker （"error": null 不算失败）、is_rate_limited（只在已判失败的结果上找 429/retry_after）、 file_mutation_result_landed（write_file 必须见 bytes_written）。 shell_hooks.py 是另一条入口：用户在 config 里配 hooks:，首个使用需逐 (event, command) 同意， stdin/stdout 走 JSON 协议、退出码 2 即拦截 pre_tool_call（Claude-Code 兼容）；默认 fail-open、 可配 fail_closed。file_safety.py 则是文件工具与 ACP shim 共用的纵深防御（HERMES_HOME/凭据 库保护等），注释明言"不是安全边界"。

    5. 结果回填与溢出¶

    结果统一走 observe → commit → project 管线（_commit_tool_result，:1064）：护栏 after_call 观察、maybe_persist_tool_result 按预算落盘并留持久化路径 （agent._tool_guardrails.record_persisted_path_for_stub 防引用桩悬空）、多模态文本部件持久化、 终态 post_tool_call 钩子（emit_terminal_post_tool_call）与 transform_tool_result （apply_transform_tool_result，内联工具也要吃到同一"every tool"契约）。≥1MB 的原始结果引用 直到全批解栈才裁（_LARGE_TOOL_RESULT_TRIM_CHARS，#70684）。工具内进度由 tool_progress_relay 的 contextvar 承载：工具在自己的线程上调 current_tool_progress()， 按 call 节流（首帧与到达 total 的帧恒通过）。

    6. 支撑件：终端环境与图形¶

    • terminal_env_provider.py：插件终端后端 ABC。历史上每个核心策略决策都是一张内置名 frozenset， 新后端会静默漏掉；现在改成一组成 声明式属性（is_remote、是否支持 cwd 持久等），ABC 直接 带分类契约。

    总结¶

    这一层的工程主轴有两个。其一，保序的并行：段规划器把"哪些调用可以同时跑"规约为三类可判定的 准入（交互屏障、路径预约、白名单/显式 opt-in），并用"读读可并行、写与任何重叠互斥"的预约表把 并发安全从"信任模型"变成"结构保证"——顺序语义一个字节没变。其二，一次产出结果线格式： 无论走哪条执行路径，最终都汇入同一个 observe → commit → project 提交管线，护栏、预算落盘、 钩子、结果变换各就各位。护栏控制器坚持"纯决策 + 运行时裁决"的分离，让同一套停滞/循环检测可以 落成警告、合成结果或受控停转三种处置——这是把复杂策略写成可测代码的范本。
