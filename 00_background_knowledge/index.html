    背景知识 —— 读懂 Hermes 需要的领域基础¶

    本篇是整套教程的地基：它不深入 Hermes 的任何具体代码，只讲后面每一篇都会反复出现的领域概念——什么是 AI Agent、什么是上下文窗口与提示词缓存、什么是工具调用与 MCP……

    目标读者：零基础。你不需要懂机器学习，只需要会基本的命令行操作、理解"一个程序调用另一个程序"是什么意思，就能顺畅读完。读后面各篇时遇到陌生术语，随时回到第 2 节的词典查询。

    1. 什么是 AI Agent¶

    1.1 LLM 本身只会"读文字、写文字"¶

    大语言模型（LLM，Large Language Model，比如 GPT、Claude、DeepSeek、Qwen 这些）的核心能力只有一件事：给它一段文字（称为提示词，prompt），它预测并生成接下来最合理的文字。它天生：

    • 没有记忆 —— 这次对话和上次对话，对它来说是两件完全无关的事；
    • 不能行动 —— 不能上网、不能操作你的电脑、不能执行命令；
    • 不知道实时信息 —— 只了解训练数据截止时间之前的世界。

    如果只把 LLM 当聊天框用，它能陪你聊天、帮你写文章，但没法"替你把活干完"。你让它"修个 bug"，它只能告诉你怎么修，不能真的动手。

    1.2 Agent = LLM + 循环 + 工具 + 状态¶

    AI Agent（智能体） 就是给 LLM 装上手脚和记性的一种程序结构。把下面四个组成部分记牢——后面所有章节都在讲它们的细节：

    组成部分 作用 在 Hermes 中的对应
    LLM（大脑） 阅读上下文、推理、决定下一步做什么 任意 OpenAI 兼容模型，一条命令即可切换
    工具（手脚） 真正执行"跑命令、读写文件、搜网页、控制浏览器"等动作 40 多个内置工具，外加 MCP 外接工具
    循环（引擎） 反复执行"模型思考 → 工具执行 → 结果回填"，直到任务完成 turn 循环（一轮对话的主循环）
    状态（记性） 保存对话历史、长期记忆、技能，让 agent 跨会话成长 SQLite 状态库 + 记忆文件 + 技能库

    1.3 Agent 循环：模型调用 → 工具调用 → 结果回填 → 再调用¶

    Agent 的工作方式可以浓缩成下面这张图。记住这张图，你就理解了 Hermes 大部分代码存在的意义——整个项目本质上就是在把这一个循环做得更稳、更快、更便宜。

    用户消息（例：「帮我看看仓库里有哪些没提交的改动」）
    │
    ▼
┌── Agent 循环 ─────────────────────────────────────────────────
│
│    (1) 组装请求：把「消息列表（历史 + 这条新消息）+ 工具清单」发给模型
│    │
│    ▼
│    (2) 模型推理：LLM 读完所有上下文，决定下一步
│    │
│    ├── 回答是「工具调用」──► (3) 执行工具：agent 进程真的去
│    │        │                  跑命令、读文件，拿到真实结果
│    │        ▼
│    │   (4) 结果回填：把工具结果追加进消息列表
│    │        │
│    │        └──────► 回到 (2)，模型带着新结果继续推理
│    │                 （循环往复，次数不固定）
│    │
│    └── 回答是「纯文本」（不再需要工具）
│             │
│             ▼
│    (5) 循环结束：这段文本就是最终回复
│
└────────────────────────────────────────────────────────────────
    │
    ▼
最终回复展示给用户，并写入会话历史（成为下一轮的上下文）

    三个关键点，请务必记住：

    • 模型不执行任何东西。 它只会输出"我想调用 terminal 工具，参数是 git status"这样的结构化请求；真正执行的是 agent 进程，执行完把结果作为一条新消息回填给模型。"模型只出主意、程序去干活"——这就是工具调用的全部秘密。
    • 循环次数不固定。 简单问题一轮就结束；复杂任务可能循环十几次，中间穿插十几个工具调用。
    • 每一轮都是一次独立的模型 API 调用。 模型没有记忆，所谓"记住"就是把之前的全部消息（包括工具结果）每次重新发一遍。这直接引出两个重要话题：上下文窗口会被占满（需要压缩），而每次重复发送的前缀其实可以缓存（提示词缓存）。

    1.4 两个常见误解¶

    • 误解一："agent 有自我意识。" 它只是把你的话、历史记录和工具结果反复喂给模型，让模型每次做下一步决策。看起来"聪明"，本质是循环 + 好工具 + 好提示词。
    • 误解二："模型能直接操作我的电脑。" 模型只能输出文字；是 agent 进程读取模型的文字请求后，替它执行。这也意味着：agent 进程有什么权限，agent 就有什么权限——安全边界在进程和操作系统层面，这也是 Hermes 安全模型的出发点。
    • 误解三："对话越长 agent 越强。" 相反，上下文塞得越满，模型注意力越分散、费用越高、速度越慢。工程上要做的是"在正确时机让上下文保持精炼"——这正是 Hermes 上下文压缩模块的职责。

    2. 核心概念词典¶

    下面 16 个术语贯穿整套教程。每个用 3-6 句话讲清，先混个脸熟；读后面各篇时随时回来查。

    术语 说明
    LLM（大语言模型） 在海量文本上训练出来的神经网络，能根据前文预测下一个词，从而生成连贯文本。它本身只会"读文字、写文字"，没有记忆、不能上网、不能执行命令。Hermes 这样的 agent 就是在 LLM 外面包一层循环和工具，让它能作用于真实世界。Hermes 不绑定任何一家模型，所有 OpenAI 兼容接口的模型都能接入。
    token（词元） LLM 处理文本的最小单位，大约相当于一个汉字或半个英文单词。模型读入和输出的所有内容都按 token 计数、计费。上下文窗口大小、模型价格、响应速度全部用 token 衡量。理解 token 是理解"上下文快满了""这次调用花了多少钱"这类问题的前提。
    上下文窗口（context window） 一个模型一次能"看到"的最大 token 数量，相当于模型的工作记忆容量。对话历史、系统提示词、工具说明、工具结果统统占用这个窗口。窗口一旦用满，最老的内容必须被裁剪或压缩，否则请求会被拒绝。Hermes 内置自动压缩机制，就是为了在窗口耗尽前主动腾出空间。
    system prompt（系统提示词） 在对话开始前就注入、用于规定模型身份与行为规则的一段提示词，模型每一轮都能看到它。Hermes 的系统提示词由身份设定、可用技能列表、记忆内容、平台上下文等多部分动态组装而成。它通常位于上下文最前面，因此也是提示词缓存的起点。
    tool calling（工具调用 / 函数调用） 让模型以结构化 JSON 声明"我想调用哪个函数、传什么参数"的机制。模型本身不执行任何东西，它只发出请求；真正执行的是 agent 进程，执行结果再作为消息回填给模型。每个工具的名称与参数说明（schema）会随每次 API 请求一并发送。Hermes 内置 40 多个工具：终端、文件读写、网页搜索、浏览器、图像分析等。
    流式输出（streaming） 模型生成答案时逐 token 返回、客户端边收边显示的方式。不开流式，用户要等整个答案生成完才能看到第一个字；开了流式，就像看打字机一样逐字出现。Hermes 的 CLI、TUI、桌面端都支持流式渲染，消息网关还会把流式进度同步到聊天平台。
    prompt caching（提示词缓存） 模型提供方的一种计费与加速机制：如果本次请求的前缀（系统提示词 + 历史消息）与上次请求完全一致，这部分就不用重新计算，费用大幅降低、响应更快。缓存按对话隔离，且一段时间不用就会失效。这解释了为什么"中途修改历史消息、增删工具"是 agent 的大忌——那会作废整个缓存前缀，让成本翻倍。
    上下文压缩（context compression） 当对话接近模型窗口上限时，把旧消息摘要成一段更短的总结、再用摘要替换原始历史的做法。它是唯一允许"改动过去上下文"的操作，因为窗口快满时，作废一次缓存换回一个能继续用的上下文，收益大于代价。Hermes 支持自动触发压缩，也可以用斜杠命令手动压缩。
    多模态（multimodal） 模型除了文本，还能处理图像、音频等其它形态输入输出的能力，比如给模型看一张截图让它分析。Hermes 通过视觉分析、语音转写、语音合成、图片生成等工具提供多模态能力。多模态内容往往体积庞大（一张图抵上千 token），如何放入上下文是一门单独的学问。
    MCP（Model Context Protocol） 一个开放协议，让外部程序以标准方式向 agent 暴露工具和资源。一个 MCP server 可以是任何进程——数据库、浏览器、智能家居网关；agent 作为客户端连接后，就能使用它注册的工具。Hermes 内置 MCP 客户端，可同时挂多个 MCP server，相当于给 agent 外接可插拔的工具包。
    子代理（subagent） 由主 agent 派生出来的独立 agent 实例：拥有自己独立的上下文窗口，并行处理一个子任务，完成后只把结论汇报给主 agent。好处是隔离——子代理翻 20 个文件产生的中间垃圾不会污染主对话的上下文。Hermes 的委派工具可以生成子代理并行干活，桌面端还能为子代理单独指定模型。
    技能（skill） 一个带元数据的 Markdown 文件夹（SKILL.md + 可选脚本），把"某类任务怎么做"写成指令，agent 按需加载。技能就是程序性记忆：agent 完成复杂任务后可以自动总结出新技能，技能在使用中还会自我改进。这是 Hermes"自我提升"的核心机制，兼容 agentskills.io 开放标准。
    插件（plugin） 用 Python 写的能力扩展包，可以注册新工具、生命周期钩子、CLI 子命令、消息平台适配器等。插件运行在 agent 进程内、拥有完整权限，所以安装第三方插件前需要人工审查。Hermes 维护官方插件目录（plugin catalog），20 来个消息平台适配器大多以插件形式发布。
    JSON-RPC 一种基于 JSON 的远程调用协议：调用方发送固定格式的 JSON 请求，被调方返回固定格式的 JSON 响应。Hermes 的 TUI 是一个独立的界面渲染进程，它与 Python 后端之间就用 JSON-RPC 通信：后端把事件（流式 token、工具进度）推给界面，界面把用户输入和斜杠命令发给后端。桌面应用与后端、代码执行沙箱也采用类似的 RPC 思路。
    SQLite / WAL SQLite 是嵌入式的单文件数据库，不需要独立数据库服务，Hermes 用它保存全部会话历史。WAL（Write-Ahead Logging，预写日志）是 SQLite 的一种工作模式，允许"一边写、多个读"并发进行，正好匹配 agent 一边聊天一边检索历史的场景。Hermes 的状态层 SessionDB 构建在它之上，还叠加了 FTS5 全文检索，让你能搜索过往所有对话。
    REPL Read-Eval-Print Loop（读取-执行-打印-循环）的缩写，一种交互式命令行环境：你输入一行，它回应一段，再等你输入下一行。Hermes 的 CLI 就是一个 REPL：运行 hermes 命令进入交互界面后，每输入一条消息就跑一轮 agent 循环。斜杠命令（如 /new、/model）也在这里输入。

    3. Hermes 的定位：一套核心，四种壳¶

    3.1 一句话介绍¶

    Hermes 是一个个人 AI 代理（personal AI agent）：你用自然语言给它派活，它通过工具真正执行，并跨会话地学习你、记住你。它由 Nous Research 开源，自我定位是"自我提升的 AI 代理"——从完成过的任务中自动总结出技能、在使用中改进技能、主动把重要知识沉淀为长期记忆。

    3.2 与同类产品的对比¶

    产品 主要形态 侧重点
    Claude Code 终端里的编码 agent 以代码仓库为中心，编程任务优先
    OpenClaw 等生活助手 消息平台上的个人助理 接入聊天软件，陪伴式日常交互
    Hermes 一套 agent 核心，跑在 CLI / 消息网关 / TUI / 桌面四种壳上 通用任务 + 生活场景 + 学习闭环 + 模型无关

    Hermes 的几个差异化特征，后面的教程会反复见到：

    • 生活在你的消息平台里。 Telegram、Discord、Slack、WhatsApp、Signal 等约 20 个平台都可以直接和它对话——背后是同一个网关进程、同一套核心。
    • 跑在任何地方。 终端执行后端有 6 种（本地、Docker、SSH、Modal、Daytona、Vercel Sandbox），所以它能跑在便宜的 VPS、GPU 集群或闲时近乎零成本的 serverless 上——不绑定你的笔记本。你在 Telegram 上说话，它在云端干活。
    • 模型随便换。 任何 OpenAI 兼容接口的模型都能接（Nous Portal、OpenRouter、OpenAI、本地端点等），一条命令切换，不锁死任何一家。
    • 自我提升闭环。 完成复杂任务后自动创建技能；技能在使用中被自我改进；周期性"自我提醒"把该记的东西写进记忆文件；还能全文检索自己的全部历史对话。

    3.3 两条设计不变量¶

    Hermes 的开发者文档明确写了两条"不可破坏"的设计不变量。理解它们，是读懂后续所有模块设计取舍的钥匙。

    不变量一：逐对话的提示词缓存神圣不可破坏。

    回顾词典里的 prompt caching：只要本次请求的前缀（系统提示词 + 历史消息）与上一次完全一致，这部分就能命中模型提供方的缓存，省钱又提速。所以任何"中途改动过去上下文"的行为都被视为大忌：

    • 改写或重排历史消息；
    • 中途增删工具集——每次 API 调用都会携带完整工具清单，工具一变，前缀就变；
    • 会话进行中重新加载记忆、重建系统提示词。

    唯一的例外是上下文压缩。配套的推论是：斜杠命令若要改变"系统提示词状态"（比如换人格、装技能），默认推迟到下一次会话才生效，想立即生效需要显式的 --now 选项。

    不变量二：核心是窄腰，能力在边缘。

    因为每次 API 调用都要把全部工具的定义发一遍，"往核心里加一个新工具"的门槛被刻意定得非常高。新能力应该优先落在这些边缘位置（按优先级排列）：

    1. 扩展现有代码 —— 能改就不新建；
    2. CLI 命令 + 技能 —— 多数能力写成"指令 + 脚本"就够了；
    3. 服务门控工具 —— 确需新工具时，用"门控函数"决定它何时可见，而不是常驻；
    4. 插件 —— 重量级扩展（新平台适配器、新记忆后端、仪表盘）全部走插件机制；
    5. MCP server —— 外部程序按开放协议把工具挂进来；
    6. 核心工具 —— 只留给"基础、通用、绕不开"的能力。

    这套阶梯保证了核心循环这个"腰"保持又窄又稳，而功能生态在边缘自由生长。

    6. 小结与自测¶

    三条核心结论：

    • AI Agent = LLM + 循环 + 工具 + 状态；Hermes 的全部代码都在打磨这一个循环。
    • 两个最重要的机制：工具调用（模型出主意、程序去执行）与提示词缓存（前缀不变则省钱提速）。
    • Hermes 的定位：一套核心、四种壳，外加"自我提升"的学习闭环；两条不变量——缓存不可破坏、核心窄腰——后续每个模块的设计都能追溯到它们。

    自测清单（能答上来就可以进入下一篇）：

    1. 用自己的话描述 agent 循环的五个步骤。
    2. 为什么"会话中途增删工具"会破坏提示词缓存？
    3. 为什么 Hermes 不轻易往核心里加新工具？新能力应该放在哪里？
    4. 消息网关和 agent 核心是什么关系？为什么 Telegram 和终端能共用同一个核心？
